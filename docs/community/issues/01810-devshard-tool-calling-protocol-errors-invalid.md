    <p>Hi @a-kuprin </p>
<p>We are interested in resolving this issue, but there’s currently no description for it.
Here’s what we’ve found in the code so far, and we are wondering whether the issue was created around this:</p>
<ul>
<li>Responses containing tool calls are not structurally validated: there is no validation of the JSON in arguments, no check that the tool name exists in the request’s tools, and no consistency check for finish_reason: "tool_calls".</li>
<li>Validation replays the generated tokens and compares the logprobs. As a result, malformed tool calls that were actually generated by the model still pass as VALID.</li>
<li>A penalty is applied only when vLLM itself returns an SSE error, and in that case it is treated as a miss, not invalid.</li>
</ul>
<p>Is there already a broader problem statement for this that we could use to write a proposal, or perhaps an existing draft/design vision?</p>
<p>We also have a few questions:</p>
<ol>
<li>What exactly is meant by “protocol errors”? Is this limited to tool calls, or does it include broader cases such as malformed SSE, invalid JSON chunks, an incorrect finish_reason, or raw tool tags appearing in content?</li>
<li>Should these cases be classified as INVALID or as a miss? This seems to conflict with the principle described in error-finish-miss.md (error = miss). Do we want to change that principle, or introduce a separate class for protocol violations?</li>
<li>Who should be considered at fault when the model itself generates invalid JSON in arguments: the host, or no one?</li>
<li>How do we distinguish client-side responsibility (for example, a bad schema or a tool_choice that the model cannot satisfy) from host-side responsibility, so that a single bad prompt cannot penalize the entire group?</li>
</ol>
