## 📝 Описание

# Dynamic devshard: per-escrow BLS DKG (NIZK dealings, on-chain T0)

**Status:** draft — design only; not implemented.  
**Related:** host-initiated close in [`finalization`](https://github.com/gonka-ai/gonka/discussions/1369).

This document specifies a **per-escrow** BLS12-381 distributed key generation (DKG) so a devshard has a **stable root public key** `PK` that a third party can check was generated by the hosts who actually dealt for that escrow. Dealings are **publicly verifiable (NIZK)**. There is **no complaint / dispute phase**.

Each listed host posts **its own** dealing on-chain. The chain **waits for a deadline**, then builds `T0` from **every** valid dealing in that window and stores `PK = ∏ A_i`. Nobody (escrow creator or “T0 sender”) gets to choose the dealer subset.

Resharing (join/leave while keeping `PK`) is specified as a follow-on. Genesis uniqueness does not depend on it.

---

## 1. Summary

Today `MsgCreateDevshardEscrow` locks funds and samples `slots` (typically 16 participant addresses). Settlement still uses **per-slot signatures**. There is no per-escrow BLS key, and the existing `x/bls` DKG is **epoch-wide**, interactive, and rebuilt every epoch.

This proposal makes escrow creation heavier:

1. Chain creates the escrow and **lists eligible participants** (`slots`) — already true. The creator does **not** pick the host set.
2. Each listed host that wants to contribute posts **`MsgSubmitDevshardDealing`** (one NIZK dealing, bound to this escrow). **This message is gas-free** for that listed host: the escrow creator already paid `CreateDevshardFee`, and the signer must be a slot that is supposed to deal, so it is not an open spam path (§6.5).
3. The chain **does not** accept a `PK` as soon as a quorum appears. It waits until `dkg_deadline`.
4. At the deadline, if there are enough valid dealings (`≥ t`, see §6.3), the chain **assembles `T0` itself** from all of them, computes `PK = ∏ A_i`, and stores both. Otherwise DKG fails.
5. The escrow is not execution-ready until DKG completes. After that, **`PK` is the close authority**: hosts can settle without the sequencer if a dispute proves user cheating.

`PK` alone is a group element and proves nothing about origin. **`T0` is the proof**, and it is a **chain-built** set of dealings, not a blob assembled by one party.

Heavier create is the cost. The **main win** is that the shard can **settle itself** with `PK` when the sequencer cheats or withholds close. Membership and telemetry are further wins from the same stable key — see **What this buys**.

---

## What this buys

The main win, then two more. All three need a per-devshard BLS key that **does not change** when the host set changes, and that **the chain can verify** without trusting the escrow creator.

### Hosts can self-close (main win)

Today `MsgSettleDevshardEscrow` requires `settler == escrow.Creator` (`VerifyDevshardSettlement`). The sequencer who opened the shard is the only party who can close it. If that user **cheats** (equivocation, invalid diffs, withholding finish/settle) or simply **never settles**, hosts cannot take the locked funds to a truthful terminal state.

A threshold signature under the shard `PK` **is** committee authorization. After an in-shard **dispute** finds user cheating (see [`finalization.md`](./finalization.md) trigger `USER_CHEATING`), hosts run finalization, aggregate `t` partial BLS signatures, and **anyone** submits settle with:

```text
MsgSettleDevshardEscrow {
  // settler need not be creator
  escrow_id,
  state_root, nonce, rest_hash, host_stats, …
  bls_signature  // ThresholdBLS(sk, domain || settlement_digest)
}
```

Chain check: `dkg_status == COMPLETED` and `Verify(PK, digest, σ)`. That replaces “signed by creator” as the close authority. Per-slot secp signatures can stay as an optional creator path or drop once BLS settle ships.

So:

- **Honest sequencer** can still settle as today (creator path, or the same BLS sig if hosts co-sign a normal close).
- **Cheating / silent sequencer** — participants **self-close** the escrow. They do not wait for the user and do not recreate the shard.
- Relayer of the tx can be any host (or a gas-free listed submitter, same idea as §6.5). Authorization is `PK`, not the Cosmos signer.

Without this DKG there is no `PK` the chain already believes; n individual signatures are a weaker, bulkier substitute and still do not rotate with membership. Self-close is why the key is on-chain.

### Membership without recreation

Today `slots` are frozen at `MsgCreateDevshardEscrow`. A host that dies, is slashed, or should be added implies **a new escrow** (new sample, new lock, new session).

With this DKG, `PK` is the shard’s identity. Join/leave is **resharing** (§11): new shares, same `sk` / `PK`. No new DKG, no new escrow, no client/settlement key rotation.

- **Remove** a host: remaining qualifying dealers re-deal their `sk_i` to the reduced set; old shares become useless.
- **Add** a host: old dealers re-deal to the enlarged set; the newcomer gets `sk'` without learning the old shares.

`T0` still proves origin (who created `PK`). Later `T_k` proves the current committee holds that same key. Telemetry and settlement keep verifying the **same** `PK`.

### Cross-devshard verifiable telemetry

Each host sits in **many** devshards. Inflight work (“how much is this host processing **right now**”) is local to a shard unless it is published. Self-signed load is cheap to lie about. A **threshold BLS signature under that shard’s `PK`** is a quorum statement:

```text
telemetry = {
  escrow_id,
  height,             // or height-sync aligned height
  loads: [ (slot_or_host, inflight_work), ... ]
}
σ = ThresholdBLS(sk, domain || telemetry)
```

Gossip `telemetry ‖ σ` among **chain participants** (hosts / controllers), not as per-inference on-chain txs. Any other devshard:

1. Reads `PK` for `escrow_id` from chain (the DKG output).
2. Checks `Verify(PK, telemetry, σ)`.
3. Treats the loads as **quorum-attested** by that shard.

No need to be in the escrow, no need for `T0` at verify time, no trust in the gossip relay. That is the same third-party story as settlement: the chain-stored `PK` is the verifier key.

Uses: avoid sending more work to a host already hot in other shards; validation / admission / routing with a shared view of in-process load.

Constraints (so this stays telemetry, not a second consensus):

- **Periodic**, height-bound, compact (counts / tokens in flight — not prompts).
- **Replay:** bind `escrow_id` + height (and maybe a monotonic telemetry nonce); ignore stale heights.
- **Not per-inference gossip.** Same bias as cPoC / finalization: flood only attestations, not every request.
- Wire, cadence, and aggregation across many escrows are a follow-on spec; this DKG is what makes those attestations **verifiable off-shard**.

## 2. Goals

1. **Joint generation** — no listed host (and no outsider) knows `sk` unless they corrupt more than the signing threshold.
2. **Binding** — `PK` is uniquely determined by this escrow’s ceremony id and the **full set of valid on-chain dealings at the deadline**. A transcript from another escrow, chain, or a **censored subset** cannot be accepted.
3. **Public verifiability** — a third party (and the chain) verifies `T0` without private shares and without a dispute round.
4. **No DKG disputes** — invalid dealings are dropped; they are not argued on-chain.
5. **Stable root key** — add/remove hosts by **resharing**, without recreating the escrow or rotating `PK` (What this buys).
6. **Reuse identities** — dealers are the escrow `slots`; encryption and dealing signatures use each participant’s already-registered secp256k1 account key.
7. **Gas-free dealings** — `MsgSubmitDevshardDealing` from an eligible listed slot charges **no fee**. Cost is prepaid by `CreateDevshardFee`.
8. **Self-close** — chain accepts settle iff `Verify(PK, settlement_digest, σ)`; creator is no longer the only closer.
9. **Off-shard verify** — any chain participant can check a shard BLS signature (telemetry, and the same `PK` as settle) against on-chain `PK`.

---

## 3. Non-goals (this document)

- Replacing the **epoch** `x/bls` DKG used for network-wide PoC signatures.
- Exact protobuf for BLS settle vs today’s `repeated DevshardSlotSignature` — the **rule** is in What this buys (`Verify(PK, …)`); field layout is an implementation item.
- Full telemetry gossip protocol (cadence, transport, cross-escrow merge). This doc only states that threshold-signed load is the payload those protocols verify.
- Extra p2p for dealings (the dealing is the chain tx; hosts decrypt their ciphertexts from on-chain `T0`).
- SNARK compression of `T0` (only if on-chain verify gas becomes a problem).

## 4. Glossary

| Term | Meaning |
|---|---|
| `n` | Number of listed hosts. Today `n = len(slots) = GroupSize` (16). |
| `t` | Signing threshold. Align with settlement quorum: `t = DevshardQuorumSlots` (`2n/3 + 1` = 11). `t` shares reconstruct `sk` / a signature. |
| Dealer / player | In genesis, the same set: every listed slot deals and receives a share. |
| `A_i` | Dealer `i`’s public contribution `g^{a_{i,0}}` (G2, BLS12-381). |
| `PK` | Root group public key `∏ A_i` over **accepted** dealers (all valid dealings at the deadline). |
| `PK_i` | Public share of participant `i`, used later for share verification and resharing. |
| NIZK dealing | One message: verification vector, encrypted shares, proofs, identity signature. Anyone can check it. |
| `T0` | Genesis transcript **assembled by the chain** at the deadline: every accepted dealing plus derived `PK`. |
| Ceremony id | Domain separator tying dealings to **this** escrow on **this** chain. |

## 5. Why NIZK (and what it is not)

A signature on `A_i` only proves identity `i` published a group element. It does **not** prove:

- `i` knows `a_i` with `A_i = g^{a_i}` (rogue-key / **contribution cancellation**: last dealer sets `A_n = PK* · (∏_{j<n} A_j)^{-1}` and knows `sk*`);
- ciphertexts are Shamir evaluations of the committed polynomial (classical Feldman needs a **complaint** round).

Two NIZKs per dealing close that:

1. **PoK of discrete log** of `A_i` (Schnorr / Fiat–Shamir), bound to the ceremony id — blocks cancellation.
2. **Share correctness** (PVSS / Groth-style NI-DKG) — ciphertexts match the verification vector and `C_i[0] = A_i`. Observers need no complaints.

NIZKs do **not** by themselves name the dealers. Long-term signatures on the dealing do. NIZKs do **not** survive as a proof if the chain only stores `PK` and throws `T0` away.

**Protocol effect:** dealing is one shot; aggregation is “keep valid dealings.” No `VERIFYING` phase, no `MsgSubmitVerificationVector`, no dispute txs. CPU per dealing is higher; rounds and control-plane complexity are lower.

## 6. On-chain create → DKG → store PK

### 6.1 Escrow create (existing, extended)

`MsgCreateDevshardEscrow` stays the listing step:

- Sample `slots` from the model epoch group (current `GetSlotsFromSorted` / `app_hash` / `escrow_id` / `model_id`).
- Lock funds, persist escrow.
- `CreateDevshardFee` (already charged at create) **pre-pays** the DKG dealing window: listed hosts do not pay per-dealing fees (§6.5).

**New escrow fields (conceptual):**

| Field | After create | After successful DKG |
|---|---|---|
| `slots` | listed participants | unchanged |
| `dkg_status` | `PENDING` | `COMPLETED` or `FAILED` |
| `dkg_deadline` | create height + `dkg_timeout_blocks` | — |
| `bls_pk` | empty | `PK` |
| `t0_hash` | empty | `H(T0)` |
| `t0` | empty | full transcript (or blob + hash; see §8) |

The escrow is **not ready for inference** while `dkg_status != COMPLETED`. Hosts that would otherwise attach on create wait for `PK`.

`dkg_timeout_blocks` is a new param: the dealing window. At that height the EndBlocker either finalizes `PK` or marks `FAILED` (refund / refusal, same spirit as `refusal_timeout`).

### 6.2 Why not one assembled `T0`

Waiting for a deadline and accepting a **quorum** of dealers is the right liveness rule (offline hosts should not fail create). That **does** open a new question if some party is allowed to **assemble** `T0`:

> How do we know the escrow creator (or whoever submits `T0`) did not simply drop some hosts’ dealings?

That is a **censorship / subset** attack, not a cryptographic NIZK failure:

- Drop honest dealers → `PK` is a product over a coalition-chosen subset. If the omitted hosts were going to contribute randomness, the remaining set may be easier to corrupt (or already is a colluding `t`).
- Accept **as soon as** `t` dealings exist → a fast coalition publishes first and locks `PK` before honest dealers land.

Two rules close it. Neither is a dispute round:

1. **Each dealer posts their own dealing.** The omitted host (or anyone rebroadcasting their signed dealing) submits `MsgSubmitDevshardDealing`. The assembler cannot “forget” a dealing that is already in state.
2. **Do not finalize at first quorum. Wait for `dkg_deadline`, then include every valid dealing in the window.** `PK` is a function of chain state at that height, not of a preferred subset.

Slots themselves are already chain-sampled at create (`GetSlotsFromSorted`). The creator does not pick who is *eligible*. The remaining trust problem is only who is *included in the product* — which must be “everyone who posted a valid dealing in time,” not “whoever the submitter packed into `T0`.”

A listed host who **never** posts is legitimately absent (offline or refusing). That is different from being censored: they had the same window and the same tx path as everyone else.

### 6.3 Dealing window

Listed hosts watch `devshard_escrow_created`. Each host `i ∈ slots` that participates:

1. Builds **ceremony id** (§7).
2. Samples polynomial `f_i` of degree `t-1`.
3. Submits **one** tx:

```text
MsgSubmitDevshardDealing {
  creator     // must be slots[j] for a unique j; one dealing per slot
  escrow_id
  dealing     // verification vector, ciphertexts for all n slots,
              // PoK, share-correctness NIZK, identity signature
}
```

Keeper accepts the dealing iff:

1. Escrow exists, not settled, `dkg_status == PENDING`, height `< dkg_deadline`.
2. `creator` is a listed slot and that slot has **no** dealing yet.
3. `dealing.ceremony_id` matches §7 (binds to this escrow / slot list).
4. Identity signature is the account key of that slot.
5. Both NIZKs verify; points are in the correct subgroup.
6. Ciphertexts are addressed to the **full** `slots` list (so every listed host, including those who deal later, can decrypt this contribution).

Invalid txs fail; they are not stored and need no complaint. Duplicate slot → reject.

Fee is **0 for the host** when the signer is an eligible listed slot (§6.5). Spam from anyone else is not fee-exempt.

Hosts **do not** finalize `sk_i` until the deadline. During the window they may fetch already-posted dealings and decrypt tentatively; the **accepted dealer set** is only known at `dkg_deadline`.

### 6.4 Deadline aggregation (chain builds `T0`)

At `dkg_deadline` (EndBlocker), let `D` be the set of stored valid dealings, ordered by slot index.

- If `|D| < t` (or a stricter `min_dealers` param, default `t`): `dkg_status = FAILED`. No `PK`.
- Else:
  - `PK = ∏_{i ∈ D} A_i`
  - Derive `PK_i` for each accepted dealer (and public evaluation points for later resharing).
  - `T0 = (ceremony_id, slots, D, PK, …)`
  - Store `bls_pk`, `t0` / `t0_hash`, `dkg_status = COMPLETED`
  - Emit `devshard_dkg_completed`

There is **no** `MsgSubmitDevshardDKG` that carries `PK`. A client-supplied product would be how omission sneaks back in.

Accepted dealers then set `sk_i = ∑_{j ∈ D} f_j(i)` from the ciphertexts in `T0`. Listed hosts who did not deal have **no** `sk_i` and cannot sign; they were eligible but not in the product.

Signing threshold is still `t`-of-`n` **shares**, but only accepted dealers hold shares. If `|D|` is barely `t`, liveness of signing is tight; that is the cost of excluding absentees. Optional: require `|D| ≥ t + f` so a few further dropouts still sign — param, not a dispute.

“`PK` is for this devshard” on-chain means: ceremony id matches this escrow, every dealing in `T0` was keeper-verified for a listed slot, and `PK` is the product of **all** of them at the deadline.

```text
MsgCreateDevshardEscrow
        │
        ▼
  slots listed (chain-sampled), dkg_status=PENDING, deadline set
        │
        ▼
  each slot → MsgSubmitDevshardDealing  (gas-free, window open)
        │
        ▼
  dkg_deadline EndBlocker
        │
        ├── |D| < t  → FAILED
        └── |D| ≥ t  → T0 := all of D, PK := ∏ A_i, COMPLETED
```

### 6.5 `MsgSubmitDevshardDealing` is gas-free

**Plan:** listed hosts submit dealings with **zero gas fee**. The creator already paid at `MsgCreateDevshardEscrow`; the message is authenticated as coming from a participant who is supposed to send it (`signer ∈ slots`, one dealing per slot, DKG still `PENDING`). That is the spam protection — not a per-tx fee.

`MsgSubmitDevshardDealing` MUST be **gas-fee free for the signer** when those checks hold. Hosts should not need a liquid fee balance just to complete DKG.

**Ante (cheap, before NIZK verify):** 0 fee only if all of:

- msg type is `MsgSubmitDevshardDealing`;
- escrow exists, `dkg_status == PENDING`, height `< dkg_deadline`;
- signer is in `slots`;
- that slot has no accepted dealing yet.

Anyone else pays the normal min fee (or is rejected). That is the spam bound: at most **one successful dealing per listed slot**, and unlisted accounts cannot ride the exemption. `n = 16` caps how many free successes exist per escrow.

**Still meter gas.** Zero *fee* is not unbounded *compute*. Each dealing has a max bytes / gas limit so NIZK verify cannot be an arbitrary-size proof. Create fee should be sized for up to `n` such verifications (plus failed attempts below).

**Failed NIZK from a listed host.** If those txs are also free and do not consume the slot, a listed attacker can loop expensive verifies. Prevent that without a dispute round:

- keep a per-escrow **prepaid verify budget** (from `CreateDevshardFee`): each dealing tx that reaches NIZK verify decrements it (success or fail);
- when the budget is exhausted, further dealing txs require a normal fee.

A listed griefer can at worst burn the prepaid budget for **this** escrow, not the whole mempool.

Implementation is an ante decorator (same family as other fee-exempt module msgs), not a change to NIZK checks.

## 7. Ceremony id

Computed by hosts **and** by the keeper. Suggested preimage (canonical protobuf / byte encoding TBD):

```text
ceremony_id = H(
  "gonka/devshard/dkg/v1" ||
  chain_id ||
  escrow_id ||
  epoch_index ||
  model_id ||
  app_hash ||          // create-time, already on escrow
  encode(slots) ||     // ordered addresses as stored
  n || t
)
```

Every NIZK challenge and every dealing signature MUST include `ceremony_id`. That is what stops:

- replaying another escrow’s `T0`;
- mixing dealers from a different slot list;
- using a `PK` generated offline, or from a subset packed by one submitter.

## 8. T0 artifact

`T0` is public. It MUST NOT contain secret polynomials or decrypted `sk_i`.

**Minimum contents:**

- version, `ceremony_id`, `n`, `t`
- full eligible `slots` (create-time list)
- **accepted** dealer set `D ⊆ slots` (those with a valid dealing by the deadline)
- per dealer in `D`: the dealing already verified at submit time
- derived `PK` and `PK_i` (recomputable)

`T0` is the concatenation of keeper-accepted dealings plus the EndBlocker product. It is not a message someone uploads.

**Storage:**

- Each dealing is already in state after its tx; at the deadline the escrow points at that set (`t0_hash` over canonical encoding).
- **Must persist** `PK` and `H(T0)`. Full dealings stay on-chain (n = 16). Do not skip NIZK verify at submit and keep only a later `PK`.

Hosts keep `sk_i` in local sealed storage (same class of problem as [`escrow-keys-at-rest.md`](./escrow-keys-at-rest.md), but for BLS shares).

## 9. Cryptographic profile (v1)

| Item | Choice |
|---|---|
| Curve | BLS12-381, `PK` and commitments in **G2** (same convention as current `x/bls`) |
| Signatures later | threshold BLS, signatures in G1, hash-to-G1 |
| Sharing | Shamir, degree `t-1` |
| Encryption | existing participant secp256k1 pubkey (ECIES as today, or HPKE if we bump registration) |
| PoK | Schnorr NIZK on `A_i`, Fiat–Shamir with `ceremony_id` |
| Share NIZK | publicly verifiable dealing (Groth NI-DKG / equivalent PVSS). Library choice is an implementation item; the **interface** is: verify dealing with only public keys + `T0`. |
| Identity sig | secp256k1 over the dealing body |

Do not use interactive Feldman + verification-vector acks for this ceremony.

## 10. Using PK after COMPLETED

- **Clients / other shards** learn `PK` from escrow query. They verify BLS signatures against `PK`. They do not need `T0` unless they audit origin.
- **Settlement / self-close (main consumer).** Chain accepts a close that carries a threshold BLS signature: `Verify(PK, settlement_digest, σ)`. The Cosmos `settler` **need not** be `escrow.Creator`. That is how participants close after an in-shard dispute on user cheating (What this buys). A cooperative creator-signed path may remain during transition.
- **Telemetry** — same verify path off-chain: gossip `Verify(PK, load_attestation, σ)` across chain participants (What this buys).
- **Partial signatures** during the session still use `sk_i` / `PK_i` among hosts; aggregation is off-chain.

Until `COMPLETED`, gateways must not treat the escrow as live.

---

## 11. Resharing (same PK — add/remove without recreation)

Join/leave **must not** run a new DKG (that would change `PK` and break settlement + telemetry verifiers). Old holders re-deal **existing** `sk_i`. Public check: `C'_i[0] == PK_i`. Aggregated constant term stays `PK`.

```text
T0 (origin, immutable)  →  T1, T2, … (custody of the same sk)
```

On-chain: new committee + per-dealer reshare msgs (same fee-exempt pattern as genesis dealings, bounded by the current committee). Keeper waits for a deadline, includes **all** valid reshares, checks they interpolate to the **stored** `PK`. Third-party **origin** is still `T0`; **current custody** is the latest `T_k`.

This is how a live escrow drops a dead host or admits a replacement **without** `MsgCreateDevshardEscrow` again.

---

## 12. Open questions

1. **Minimum `|D|`.** Default `t` (11 of 16) matches signing quorum. A higher `min_dealers` (e.g. `n-f`) makes post-DKG liveness safer if more hosts drop. Not a trust issue if §6.2–§6.4 hold.
2. **Warm vs cold key.** Dealings must be signed by the same key the chain uses to identify `slots[j]` (cold / account). Warm keys stay for session traffic, not for DKG identity.
3. **Library.** Pick one NI-DKG implementation (e.g. Groth 2021-style) and freeze proof encodings before proto freeze.
4. **Failed DKG refunds** — exact reuse of `refusal_timeout` vs a dedicated DKG fail handler.

---

## 13. Contrast with current `x/bls` epoch DKG

| | Epoch `x/bls` today | This proposal |
|---|---|---|
| Scope | whole epoch validator set | one escrow’s `slots` |
| Lifetime | new key every epoch | `PK` stable for the escrow |
| Dealings | Feldman + private share check | NIZK / PVSS, public |
| Phases | DEALING → VERIFYING → COMPLETED | dealing window → deadline aggregate `T0` |
| Disputes | verification vectors / implicit complaints | none (invalid dealing = failed tx) |
| Proof of origin | not aimed at third parties per escrow | chain-built `T0` on the escrow |
| Chain role | collect parts, then aggregate `C_k0` | verify each dealing, at deadline `PK = ∏ A_i` over **all** of them |

Do not overload `InitiateKeyGenerationForEpoch` for devshards.

---

## 14. Implementation sketch (when scheduled)

1. Params: `dkg_timeout_blocks`, optional `min_dealers`; proto fields on `DevshardEscrow`; `MsgSubmitDevshardDealing`.
2. **Ante: `MsgSubmitDevshardDealing` is gas-free** when signer is a listed slot with no dealing yet (§6.5), plus prepaid verify budget so failed NIZKs cannot loop for free forever.
3. Host: ceremony id, NIZK deal, submit own dealing **with 0 fee**, at deadline decrypt `T0` and persist `sk_i`.
4. Keeper: §6.3 per-dealing checks; EndBlocker §6.4; refuse inference/settle until `COMPLETED`; under-quorum → `FAILED`.
5. Tests: cancellation NIZK fails; wrong `escrow_id` rejected; duplicate slot rejected; **omitted dealing still counts if the host posted it**; finalize only at deadline (early quorum must not lock `PK`); `PK = ∏ A_i` over full `D`; timeout; **unlisted signer is not fee-exempt**.
6. Later: **BLS self-settle** (`Verify(PK, …)`, creator no longer required); reshare `T_k` (add/remove hosts); threshold-signed load attestations gossiped across chain participants.

One thing worth knowing before you settle the "failed DKG refunds" question, since it touches the
mechanism you would most likely reuse: the existing refund-on-failure path is currently not wired up.

`InvokeSetBlsHooks` (`x/bls/module/module.go:243`) asks depinject for `*keeper.Keeper`, while
`ModuleOutputs` provides the keeper by value (`module.go:214-218`). Nothing provides the pointer,
invoker dependencies are optional, so the parameter arrives nil and the guard at the top returns
without calling `SetHooks`. `Hooks()` then keeps returning the empty implementation, and both
`AfterThresholdSigningFailed` and `AfterThresholdSigningCompleted` are no-ops in any app built this
way. I confirmed it in a simulation run where a bridge mint's signature expired after the usual three
attempts and the inference-side failure hook never fired.

Filed with the details in #1749. Raising it here because a per-escrow DKG that leans on the same

I like the original idea, especially removing the sequencer as the single authority capable of closing an escrow. A chain-verifiable committee authorization mechanism would make devshards substantially more resilient to a cheating or unavailable sequencer.

My main concern is the increase in **devshard startup time**.

Today, escrow creation requires one transaction and the shard can start almost immediately. With the proposed DKG, the escrow remains `PENDING` until `dkg_deadline`, even if enough—or all—dealings arrive earlier. Depending on `dkg_timeout_blocks`, this could increase startup time from roughly one block to tens of seconds or more.
